TASA CRM · Telephony Integration Audio path broken

No audio on browser softphone calls

SIP signaling works correctly and ICE IS being negotiated — but every ICE candidate Asterisk offers is a private LAN address. No browser outside those subnets can ever complete a media connection. CRM-side WebRTC code has been independently reviewed and is not the cause.

PBX sip.grcti.com · FPBX-17.0.33 (Asterisk 20.21.0) Extension tested 1006 → echo test *43 Captured fresh live SIP/SDP trace, re-run today — not the original stale capture

This supersedes the original version of this document, whose "no ICE candidates at all" finding is no longer accurate — ICE has since been at least partly enabled. Re-running the same diagnostic against the live PBX today shows ICE negotiation happening, but every candidate Asterisk offers is still unreachable from outside its own LAN, which produces the identical symptom: signaling connects, audio never flows.

Symptom vs. cause

Confirmed working REGISTER, INVITE, 200 OK all exchange correctly over wss://sip.grcti.com/ws. The CRM browser client correctly gathers its own public server-reflexive (srflx) ICE candidate via STUN (verified live) — the client is not misconfigured.
Confirmed broken Asterisk's SDP answer offers only private LAN candidates — no public/srflx candidate of its own. A browser on the public internet has nothing reachable to connect to.

Two things this proves, precisely:

ICE is running, but incompletely ice-ufrag/ice-pwd and two typ host candidates ARE present — ICE support is at least partially on. But Asterisk never performs its own STUN/NAT reflexive discovery, so it never offers a typ srflx candidate pointing at its real public IP.
Two different private subnets, neither public The two host candidates come from two different private interfaces — 172.16.10.0/24 and 10.240.4.0/24. Whatever machine/container Asterisk's media (RTP) engine is bound to, it has interfaces on both, and advertises both, but never its actual internet-facing address.

What the PBX administrator needs to check

PJSIP WebRTC transport (the one bound to the WSS listener) + RTP/NAT config

These are investigation items, not assumed values — the previous version of this document guessed a specific public IP (118.185.152.22) and that guess should not be trusted or reused without confirming it against the PBX's actual current network config.

1
Server / network config, not FreePBX GUI Confirm the PBX's actual current public IP address (the one the internet reaches it on today). Do not assume the value from any prior document.
2
FreePBX → Settings → Asterisk SIP Settings → NAT Settings, or the pjsip transport config directly (the transport bound to the WSS listener) Check whether external_media_address is set at all, and if so, whether it matches the confirmed public IP from step 1. external_media_address
3
Same transport block Check whether external_signaling_address is set and matches the same confirmed public IP. external_signaling_address
4
Same transport block Check local_net — today's evidence shows Asterisk's media engine spans two private subnets, so if this is configured at all, confirm both are listed, not just one. local_net = 172.16.10.0/24
local_net = 10.240.4.0/24
5
Extension template / endpoint used by 1000–1999, Advanced/WebRTC tab Confirm ice_support is actually yes (today's evidence suggests it likely already is, since ICE attributes ARE present — verify rather than assume). ice_support
6
rtp.conf (some FreePBX versions keep a second copy of steps 2–4 here) Confirm the RTP layer's own icesupport / externaddr / localnet agree with whatever is found in steps 2–5. Mismatches between pjsip.conf-level and rtp.conf-level settings are a common cause of exactly this symptom.
